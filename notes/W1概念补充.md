## 一、先纠正一个根本误解

**你以为的"大模型"**：一个能理解问题、去数据库查资料、推理出答案的智能程序。

**真实的大模型**：一个函数，输入一串 token，输出"下一个 token 的概率分布"。

```
输入:  "Agent 通过工具"
输出:  { "调用": 51.8%, "执行": 23.4%, "与": 11.8%, ... 其余 397 个 token 分摊剩余 }
```

**没有数据库，没有 if-else，没有"理解"。** 只有矩阵乘法。

那"回答一个问题"是怎么发生的？靠一个循环：

```
while 没结束:
    probs = 模型(已有的全部文字)     # 算下一个 token 是啥
    next  = 从 probs 里挑一个        # 采样
    已有的全部文字 += next           # 接上去
```

**这一个循环，就是后来所有 Agent 框架（LangGraph、AutoGPT…）的原子结构。**
W3 要手写的 ReAct，本质就是把这个循环加上"工具调用"和"停止条件"。

> 实验 E1 让你亲眼看到这个概率分布。

## 二、这些概念你其实早就懂了

| LLM 概念 | 你熟悉的对应物 | 差异点 |
|---|---|---|
| **Token** | 字符串切分 / 序列化单位 | 按**字节级统计频率**切，不为人类可读性服务 |
| **Embedding** | 把对象映射成特征向量 | 语义相近 → 向量方向相近，可以做距离计算 |
| **Attention** | 带权重的 JOIN / 加权聚合 | 权重是**算出来的**，不是配置的 |
| **KV Cache** | MySQL buffer pool / Redis 缓存 | 缓存的是矩阵，不是对象；决定显存与并发上限 |
| **LoRA 微调** | 不改主干，加插件覆盖行为 | 用两个小矩阵的乘积去"补丁"原权重 |
| **RAG** | 先查再答（搜索引擎 + 摘要） | 检索结果拼进 prompt，不是改模型 |
| **Prompt** | 函数参数 / 配置 | 但它是**自然语言**，所以不稳定、可被注入 |
| **Agent** | 状态机 + 任务编排 | 状态转移由模型"猜"出来，不是写死的 |
| **Token 计费** | 按流量/调用次数计费 | 但按 token 数（中文比英文贵 2~3 倍） |
| **上下文窗口** | 请求体大小上限 | 超了要截断/压缩，且越长越贵越"走神" |
| **幻觉** | 服务返回了错误数据 | 不是 bug，是**设计使然**：它只会猜最可能的字 |
| **temperature** | 随机因子 | 控制分布的"尖锐程度" |
| **梯度 / 反向传播** | 根据误差调整参数 | 唯一需要新学的数学，但可以只用直觉理解 |

**注意最反直觉的一条**：`幻觉` 不是缺陷。模型的训练目标是"让下一个 token 概率最大"，
它没有"我不知道"这个选项——除非你专门训练它拒答，或者用 RAG 给它资料、要求它引用。

## 三、完整流程走一遍（Java 程序员视角）

假设用户问："Agent 通过工具做什么？"

```
① 分词 (tokenize)
   "Agent 通过工具做什么？"
   → [1234, 567, 89, 2024, 31]        ← 数字 ID 序列
   对应：把对象序列化成字节流

② 查表 (embedding)
   每个 ID → 一个 4096 维向量
   → 形状 [5, 4096]
   对应：把 ID 映射成特征向量（类似 one-hot，但是稠密的语义向量）

③ 堆叠 N 层 Transformer（本实验 4 层，GPT-3 是 96 层）
   每层做两件事：
   ├─ 注意力：让每个位置"看"前面的位置，决定该从谁那里取多少信息
   │         对应：带权重的关系 JOIN，权重由内容算出
   └─ 前馈：  对每个位置独立做非线性变换
             对应：单行数据的特征变换
   中间用残差连接（= 直通线，保证梯度能传下去）

④ 输出层
   最后一个位置的向量 → 乘上词表矩阵 → 400 个分数（本实验）
   → softmax 变成概率分布

⑤ 采样
   按 temperature / top_k / top_p 挑一个 token

⑥ 回到 ①，把新 token 接到末尾，重复
```

**关键点：没有任何一步是"理解语义"。全程是矩阵乘法和查表。**

那为什么它能回答问题？因为**训练**把"语言的统计规律"压缩进了那些矩阵里
（本实验 85 万个数字，GPT-3 是 1750 亿个）。规律是从海量文本里统计出来的。

> 实验 E2 让你看到 loss 从 5.99（瞎猜）降到 0.004（几乎全对）的过程。

## 四、关于"手写"，你可能想问

### Q：为什么不用 PyTorch？业界都不用自己写吧？

**对，生产绝不用自己写。** 这是**训练手段，不是交付物**。

就像你学 Java 时老师让你手写 `HashMap`——你工作中用 `java.util.HashMap`，
但理解哈希冲突和扩容机制，让你在排查性能问题时知道该看哪里。

手写一遍你能得到三样东西：

1. **面试通过的能力**。面试官问"KV Cache 显存怎么估算"，只会调框架的人答不上来。
2. **排查线上问题的能力**。Agent 跑偏时，你得判断是模型问题、上下文问题、
   还是位置编码问题——框架不会告诉你。
3. **做技术决策的能力**。什么时候该用 RAG、什么时候该微调、上下文该留多长，
   这些判断依赖对底层机制的理解。

### Q：我写的这个玩具和 GPT-3 差 20 万倍参数，有什么意义？

机制**完全一样**，只是矩阵更大。就像 mini 版 Redis 和真 Redis：
数据结构、缓存淘汰、持久化思路都相同，只是规模不同。

实验 E9 专门讲了这一点。

## 六、读代码时抓住这几根主线

读 `mini_gpt.py` 时不要逐行看，先抓住这条数据流，再往细节钻：

```
idx (B,T)                    整数 token ID
  ↓ wte[idx]                 查表 → (B,T,C)  ← 把 ID 变成向量
  ↓ + wpe                    加上位置向量      ← 让模型知道顺序
  ↓ Block × N                注意力 + 前馈     ← 信息交换与变换
  ↓ norm_f                   归一化
  ↓ @ wte.T                  乘以词表 → (B,T,V) ← 每个位置对所有 token 打分
logits                       分数
```

**反向传播**只需要抓住一句：`loss` 对每个参数的偏导数（梯度），
告诉我们"这个参数该往哪个方向调、调多少"，然后微调它。重复几十万次。

## 七、一句话总结 W1 到底做了什么

> 你手写了一个**最小可用的大模型推理 + 训练引擎**，覆盖了从"文字"到"下一个字概率"
> 的完整链路，并用数值梯度校验证明了它是对的。
>
> 你现在应该能解释：模型为什么会胡说、上下文为什么有限、Token 为什么决定成本、
> KV Cache 为什么省时间但吃显存。

**这些认知是后面所有内容的地基**：W2 的 RAG 是在解决"模型不知道事实"，
W3 的 Agent 是在解决"模型不能行动"，W4 的 MCP 是在解决"工具不能复用"。
每一个都是在补大模型的某个固有缺陷——而你刚刚亲手确认过那些缺陷确实存在。
